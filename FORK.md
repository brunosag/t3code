# T3 Code fork

The user's fork of upstream T3 Code. Where this file and `AGENTS.md` differ, this file wins. Fork notes go here, not in `AGENTS.md`, which upstream edits almost daily.

## You may

- Land finished work on `bsag`, started from `origin/bsag` (never the stale local `main`), unless the user asked to review it first. Pushing `bsag` deploys (below). Don't ask first: run the fork check, push, watch the deploy and check the result live, then report.
- Skip upstream's process: Pull requests, Evals, Documentation, the bug-proof rule under Verifying (failing test first, before/after captures) and the ask-first browser rules don't apply.
- Write fork-only UI in English, without upstream's translation wrappers; `t3code/no-untranslated-copy` is a warning in the fork (`vite.config.ts`), so it doesn't block commits.
- Check user-visible changes on the deployed instance after the deploy (`~/local/t3-pi/DEPLOYMENT.md` on `vps` says how to reach it). A worktree dev server costs a ~4 GB install and a seeded database (the live one is past the 500 MiB auto-seed limit: `vp run migrate-dev-db`); start one only when a change can't be seen deployed or shipping it unseen could break the live instance.

## Limits

- Before pushing, run `scripts/fork-check.sh`, the deploy's own gate (`vp run check:changed origin/bsag` is optional: its default base is upstream's `main`, so it diffs the whole fork for over ten minutes).
- Surfaces are the server with its web client on `vps`, the Linux desktop build and the Android app; macOS, Windows, iOS and the relay only when asked.
- The Android app (`apps/mobile`) is the fork's own build, `com.bsag.t3code`, installed next to upstream's Play Store app. It can't use upstream's T3 Connect sign-in, relay pushes or OTA updates, so it gets notifications from the fork's server directly (below). Keep iOS-only code as upstream has it.
- Keep `packages/provider-pi` identical to upstream. Don't restore the removed V1 adapter or permission layer.
- The live installation is `~/local/t3-pi` on `vps`; preserve its `userdata` and keep development state separate. Back up its database before deploying a migration; reverting the executable is not a database rollback.
- `t3 service restart` on the host interrupts running agents; otherwise the server switches to a deployed version by itself once agents are idle.
- Enable `SERVER_RELEASES_PUBLISHED` (`apps/server/src/cloud/selfUpdate.ts`) only when matching release artifacts exist; fork server releases are not published.
- The npm-installed server loads `@ff-labs/fff-node` through an ESM import (upstream's single-executable path needs a patched CommonJS export the npm package lacks); changing that import means changing the installation layout too. npm skips pnpm patches, so the deploy applies the fff-node and `@cursor/sdk` patches to the host's copies (the search index calls fff-node's patched async methods) and fails when npm installed a version a patch wasn't written for; `scripts/fork-check.sh` fails when a version bump leaves the workflow naming a missing patch. node-pty's patch is Windows-only, and npm resolves its caret range past the pnpm pin.

## Deployment

A push to `bsag` runs `.github/workflows/deploy-fork-vps.yml`: it runs the fork check, builds the server with its web client, and installs the npm tarball on `vps` over Tailscale with `t3 service install --defer-restart`, which selects the version (`activeVersion` in `~/local/t3-pi/runtime/service-state.json`) without restarting. Watch the run (`gh run watch`); the deploy is live when `serverVersion` from `/.well-known/t3/environment` on the server's port ends in the pushed commit's 9-character SHA. `[skip ci]` in a docs-only commit message skips the deploy. Linux desktop builds publish fork prereleases through `.github/workflows/desktop-fork-linux.yml`. Android builds publish signed `android-<date>.<run>` prereleases through `.github/workflows/mobile-fork-android.yml` when a push touches the app or its packages; its signing key, Firebase files and build environment live in `~/.config/t3-fork-android` on the laptop (source `env.sh` and `signing.env`, then `expo prebuild --clean --platform android` and `./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` with `APP_VARIANT=production`), and the same key is in the repository's `FORK_ANDROID_*` secrets. Host procedures are in `~/local/t3-pi/DEPLOYMENT.md`.

## Upstream merges

- Merge upstream into a review worktree and run `scripts/fork-check.sh` before updating `bsag`. In a conflict, take upstream's side unless it touches a retained change below.
- Before pushing a merge, check it for new migrations (`apps/server/src/persistence/Migrations/`) and, if there are any, back up the live database first: pushing deploys, and the server migrates as soon as agents go idle.
- Only the fork workflows (`deploy-fork-vps`, `desktop-fork-linux`, `mobile-fork-android`) run; every upstream workflow is disabled (`gh workflow disable -R brunosag/t3code <file>`), since their stuck runs once got the fork's Actions paused, which stopped deploys. After each merge, disable any newly arrived one.
- The desktop app stages only the server dependencies matched in `scripts/lib/cli-external-packages.ts`, never their peers. When a merge bumps one of those and a dependency becomes a peer, declare it in `apps/server/package.json`, or the AppImage backend crash-loops on a missing module and the app never opens.
- A new retained change gets a line below and a test in `scripts/fork-check.sh`, so a merge that breaks it fails.

## Retained changes

- **Claude thinking quotes:** no quoting on Claude thinking items; the Claude adapter strips saved thinking citations but keeps user comments.
- **Question drafts:** written answers to agent questions survive reloads; choosing an option moves the answer into the thread draft.
- **Compaction:** a snoozed thread, and a settled one that its own agent settled or an enabled `continue` schedule will resume, still gets idle compaction (from 100K tokens) and stays settled or snoozed through it.
- **Schedules:** a late or manual interval run keeps the previous grid; missed runs of every type run late once (upstream skips fixed-time runs missed by over 10 minutes); `schedule_task` updates take a `delegate_task`-style `target`, and the web editor sets options with the traits picker.
- **Fast Mode switch:** the server can disable Fast Mode, saved selections and delegated tasks included.
- **Read aloud:** local speech synthesis (Phonon 31M through `phonon-tts`'s threaded WebAssembly build in a child Node process; Kokoro voice ids saved earlier decode to the default voice; tested in `speechText.test.ts`, `SpeechSynthesis.test.ts` and `settings.test.ts`); a read aloud model set in Settings → Chat rewrites each reply for listening first (code, paths, maths, symbols, tables and code blocks), through the voice-cleanup text generation call so no provider adapter changes, and a failed rewrite shows its reason instead of reading the rule-based text (tested in `readAloudScript.test.ts`); a player above the composer that survives thread switches; a running turn's latest finished message can be read from its hover row (upstream reverted that row; tested in `MessagesTimeline.logic.test.ts`). No speech controls for guests. The Android app has it too, from a message's action row, with a draggable timeline (`ReadAloudTimeline.android.tsx`) and its voice in Settings → Voice; web and mobile share the player logic in `packages/client-runtime` (tested in `readAloudController.test.ts`, and the Expo playback adapter in `expoPlaybackAudio.test.ts`).
- **Context window on Android:** the composer shows how full the thread's context window is, as a percentage over a hairline that fills with it (the token count when the provider reports no window size); tapping it opens the in-thread usage card, which lists the context window, with a tick where auto-compaction starts, above the account limits, and opens for providers with no limits too (tested in `contextWindow.test.ts`).
- **Model picker on touch:** touch or pen doesn't focus the search, so the on-screen keyboard stays down; it decides per pointer event (`focusesModelPickerSearch`), replacing upstream's `(pointer: coarse)` check, which misses pens and touchscreen laptops.
- **Sharp sheets:** sheets and the sidebar's provider update pill don't keep `will-change: transform`, which leaves text blurry after the slide.
- **Theme editor:** the role spotlight pauses while a color picker is open.
- **Project groups and defaults:** a title every grouped project shares names the group; provider-selected repositories and owner/repo shorthand clone over SSH; Settings chooses the base directory for new projects.
- **Background work:** Linux holds a sleep and lid inhibitor while agent work is unfinished (not pull-request watches), switched by upstream's "Keep awake while agents work" setting; upstream's `KeepAwake` stands down on Linux so only one lock is held; the desktop tray stays, and its startup call is tested in `DesktopApp.test.ts` (an upstream merge once dropped it).
- **Limits hub:** a turn failed on CLIProxyAPI cooldown without a `reset after` time takes its reset from the Limits hub; hubs can be renamed; the Limits view hides and reorders providers, limits and account rows, pools accounts by plan size with burn, runway and charts, and the server records hub readings in `usage-limit-history.json` even with no client open. Claude hub figures use, per window, whichever is newer of the latest valid traffic headers in `auth-files` (including Fable and quota cooldowns) and the OAuth usage reading, so a reset redeemed outside the server shows at the next usage read (a 5-hour header whose reset has passed while the weekly window is still active resets to 0% used); OAuth usage metadata is probed at most hourly per login (failures included), invalidated after redemption, and HTTP 401/403 auth failures surface immediately without carrying old readings or headers (recovering as soon as the hub status or a fresh header changes). A failed hub read of a login keeps its last good reading for up to an hour (Anthropic answers close reads with 429); upstream keeps it with no time limit, and the fork keeps the hour along with upstream's same-hub, same-login checks, noted under the provider once it is two default refresh intervals (10 minutes) old (tested in `usageLimits.test.ts`) and left out of the history. Switched-off hub logins never raise failed-read notices, and an unused session (`0%` used, no clock) blocked behind a spent weekly quota carries over the weekly reset time. Dragging a hub login's row in the Limits view sets CLIProxyAPI's routing priority (top first), and the provider menu's "Route by earliest reset" has the server keep a hub's logins in order of their longest limit's reset, soonest first, re-sorting after each read (tested in `UsageLimitSources.test.ts`); the provider menu's "Hub accounts" switches logins on and off in the hub, listing a hub that several machines read once, and switched-off logins stay as dimmed rows outside the pooled totals and never count as serving a model, so upstream's hub routing (thread card, cooldown reset) leaves them out (tested in `UsageLimitSources.test.ts`). Hub Claude logins show and redeem banked resets by kind, Fable apart from weekly (upstream offers kinds only to local instances); each kind sits on its account's row of the limit it refills, showing its count and soonest expiry and opening every reset's expiry, and redeems the soonest to expire (tested in `usageLimits.test.ts` and `claudeResetCredits.test.ts`); Claude only offers them to a recent Claude Code, so hub reads present the newest version a Claude instance reported (tested in `cliproxyApi.test.ts`). The Android app has the pooled view with runway charts, hidden and reordered providers and limits, banked resets by kind, and a Hub accounts screen (switch logins, drag routing order, earliest-reset routing, hub names); its controls share their logic with the web in `packages/client-runtime` (tested in `usageLimitControls.test.ts`).
- **Shared provider settings:** provider and hub settings (instances both machines have, new instances, hub names and login profiles, model favorites, hidden models and order) stay equal on every connected machine, keeping each machine's paths, keys, setup mode and environment variables. Edits copy across as they're made, and a client keeps machines that still differ in sync on its own after a 5-second settle: its own machine wins where both set a value, and a hub login profile only one machine has reaches the others. ACP Registry agents, onboarding, and hubs or instances only one machine has stay per machine (tested in `sharedProviderSettings.test.ts`).
- **Spelling dictionary:** the desktop's spelling menu has Add to Dictionary for the app's own pages (not previews), and Settings → Chat lists the added words with a way to remove each (Linux and Windows; macOS's system spellchecker can't be listed).
- **Thread models from the CLI:** `t3 thread model <id>` reads or sets the model and options a thread runs on, `t3 thread models` lists what the environment can run, and `t3 thread show` prints the thread's options; Shin picks and reports its threads' models through them (tested in `cli/thread.test.ts`).
- **Installed web app names:** `manifest.webmanifest` is named `T3 Code (<environment label>)`.
- **Stable branding:** the served web client and Linux desktop build use the black production icons and plain "T3 Code"; the desktop's Electron runtime name stays "T3 Code Nightly" so its keyring state doesn't move.
- **Deploys wait for idle agents:** `t3 service install --defer-restart` switches within about 10 seconds of the last agent work ending (a 5-second settle covers a queued follow-up starting), or after 24 hours; the running server reads only the selected version from the service state, so an upstream launcher protocol bump can't leave it unable to see a deploy (tested in `IdleRestart.test.ts`).
- **Agent memory on small hosts:** `T3CODE_AGENT_MEMORY_HIGH`, `_MAX` and `_SWAP_MAX` override the agents slice's limits; `check:changed` runs its steps one at a time under 6 GB free.
- **Orphaned desktop backends exit:** the backend gets the desktop's pid at bootstrap and exits if it dies (an AppImage update under `appimage-run` does this).
- **No swipe navigation:** horizontal wheel input never moves through threads; upstream's `HistorySwipeNavigation` is deleted, so a merge that edits or mounts it conflicts or fails the fork check's typecheck.
- **AppImage updates restart under appimage-run:** the relaunch helper waits for the updating app's pid to exit before running the new AppImage, since appimage-run's bubblewrap (`--die-with-parent`) kills a new instance started as the old app's child; it relaunches through `T3CODE_DESKTOP_LAUNCHER_PATH` when set and the AppImage kept its path; tested in `ElectronUpdater.test.ts`.
- **Hidden desktop start:** `--hidden` (the laptop's login autostart) loads the window without showing it; tested in `DesktopWindow.test.ts`.
- **Automatic downloads, installs and provider updates:** the desktop app downloads an offered release after each check or track switch (not one that failed to apply) and installs it like a VPS deploy: once its backend's `agent-work-running` marker has been gone 5 seconds, or after 24 hours, but only after 30 seconds without keyboard or mouse input (or a locked screen); an app with no visible window relaunches hidden (tested in `DesktopUpdates.test.ts` and `ElectronUpdater.test.ts`); the server updates a provider once no active thread uses any instance of its driver, once per release (tested in `ProviderAutoUpdate.test.ts`).
- **Installation and desktop fixes:** provider updates recognize npm ownership before native-looking layouts; Linux desktop entries need the `--class` switch upstream dropped; development can omit Electron, reuse the last server build (`dev:desktop:lean`), open DevTools explicitly and exit when its window closes; desktop dev origins stay out of the server's embedded web client.
- **Server-sent Android pushes:** the fork's Android app registers with each server (`server.registerMobilePushDevice`), and the server sends its agent activity pushes through Firebase itself, with the relay's FCM data, from every state `AgentAwarenessRelay` publishes, T3 Connect linked or not; devices live in `mobile-push-devices.json` and credentials in `fcm-service-account.json` in the state directory (`<T3 home>/userdata`). The card and alert data come from `infra/relay`'s payload modules, imported and bundled; the FCM request and the two Android alert builders are copies of the relay's `FcmClient` and `FcmDeliveries`, so a merge that changes those needs the same change in `apps/server/src/mobilePush` (tested in `MobilePush.test.ts` and `AgentAwarenessRelay.test.ts`).

## Test fixtures on this machine

- `Cannot read properties of undefined (reading 'config')` at collection: use the checkout's `node_modules/.bin/vp`, not a global `vp` (mismatched Vitest).
- Bare-repository fetch fixtures that map into `refs/heads` use `--no-prune`; an inherited `fetch.prune=true` can delete the mapped branch.
- Subprocess identity fixtures use a real executable (`process.execPath`, Bash for WSL fixtures) and a readiness signal: NixOS multicall coreutils may exit when copied under another name or drop a custom `argv[0]`. Don't assume `/usr/bin/node` or `/bin/ps`.
- Private IPC tests reject a `/tmp` owned by another user: set `TMPDIR` to a short, owned mode-700 directory.
- `vp run` prepends checkout binaries to PATH, shadowing shims. Browser-free runs need `--exclude` for `**/*.browser.test.*` and `**/ServerBrowserPage.test.ts`.
